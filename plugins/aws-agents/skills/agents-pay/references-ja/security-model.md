# agents-pay のセキュリティモデル

脅威モデルと、各制御がどのように強制されるかをまとめています。`scripts/` の何かを変更する前にお読みください。過剰に慎重に見える動作のいくつかは、重要な役割を果たしています。

## 対象範囲: これは実行時のスキルである

何よりも先に述べておく価値があります。同じ仕事をしているように見える、隣接するスキルがあるためです。

| | `agents-build` → `references/payments.md` | `agents-pay`(このスキル) |
|---|---|---|
| 問い | 「**作っている**エージェントに、支払う能力を与えるにはどうすればよいか」 | 「このエージェントは、**いま**、これに支払う必要がある」 |
| いつ | ビルド時、出荷する製品の中で | 実行時、いま手元のセッションの中で |
| ウォレット | その製品の**エンドユーザー**ごとに 1 つ | このインストールに 1 つ |
| 支出を承認するのは誰か | 製品自身のフロー | ターミナルにいるオペレーター |
| ここでの脅威モデル | 製品の顧客 | **登録された支払いツールを経由する、悪意のあるモデルの入力** |

最後の行が、このスキルが別に存在する理由です。製品が、自前の承認フローで顧客ごとにセッションを発行する場合、エージェントは、作者が制御するシステム内の一部品です。エージェントが、タスクの途中で**オペレーターの**お金を支出する場合、エージェントは侵害されるかもしれない対象であり、すべての上限がエージェントに対して維持されなければなりません。`auto_session=True` は、ビルド時のガイダンスとしては有効ですが、使い果たされた予算をランタイムが置き換えられるため、このスキルには適しません。

どちらも間違いではありません。答える問いが異なり、`agents-build` は、このブランチでは手を加えていません。

## ゲートは、通過するものだけをカバーする

信頼の表の前に述べておく価値のある、境界の条件です。これらの制御のどれも持っていないのに、持っていると思い込む状態に陥る、最も簡単な方法だからです。

Strands と LangGraph は、AgentCore Payments の統合(`AgentCorePaymentsPlugin`、`AgentCorePaymentsMiddleware`)を提供しており、**あらゆる**ツール呼び出しからの `402` をインターセプトして決済します。`x402_fetch` を登録するよりも、確かに便利です。しかし、これらはこのスキルのまったくの外側にあります。支払いはフレームワーク自身のラッパーの内部で行われるため、`x402_policy.py` が参照されることはありません。

その具体的な代償:

| 制御 | `x402_fetch` 経由 | ネイティブなプラグイン / ミドルウェア経由 |
|---|---|---|
| 1 回あたりの上限 | 強制される | **ない** |
| オリジンの許可リストと SSRF の審査 | 強制される | **ない** |
| 導出された冪等性トークン | 強制される | **ない** — 呼び出しごとにランダム |
| 審査を通った `accepts` のエントリだけが署名者に渡る | 強制される | **ない** |
| 証明をモデルのコンテキストの外に保つ | 強制される | 統合による |
| ランタイムのロールからセッションの作成を外す | 強制される | **`auto_session=True` はそれを必要とする** |

セッションを発行できるエージェントは、使い果たした予算を、より大きなものに置き換えられます。そのため、セッションごとの上限は、何も制限しなくなります。

**同じプロセスで、両方の経路を動かさないでください。** ネイティブな統合が有効で、*かつ* `x402_fetch` が登録されている場合、どちらが特定の `402` を決済するかをモデルが選ぶため、ゲートは助言に過ぎなくなります。どちらか一方を選んでください。オペレーターのお金を、オープンなウェブに対して支出するエージェントには、`x402_fetch` を選びます。それでもネイティブな経路を使う場合は、最低限、予算が人間から来るように、明示的な `payment_session_id` を渡してください。

## 信頼の境界

| コンポーネント | 信頼するか | 認証情報を保持するか | 実行する主体 |
|---|---|---|---|
| ターミナルのオペレーター | はい — 権限の根源 | はい(CLI のウィザード経由) | 人間 |
| `agents_pay_admin.py` | はい | 人間から渡された間だけ、一時的に | 人間 |
| `~/.agents-pay/config.json` | はい — 認可の記録 | いいえ | 人間が書き込み、ランタイムが読み取る |
| `x402_policy.py` | はい — 判断の起点 | いいえ | プロセス内、ランタイム |
| `x402_fetch.py` | はい — トランスポート | いいえ(証明は一時的) | プロセス内、ランタイム |
| モデル / エージェントのループ | **いいえ** | いいえ | — |
| 発行元の HTTP レスポンス | **いいえ** — 悪意のある入力 | いいえ | — |

モデルは、脅威モデルの外側ではなく、内側にあります。悪意のあるモデルの入力が、登録された支払いツールに届いても、制御は維持されます。同じ OS アイデンティティと AWS 認証情報の下で、制限のないコードが実行されるのは、ホストの侵害であり、別のプロセス、コンテナ、OS アカウント、IAM の境界が必要です。

## 実行可能な制御が重要な理由

このスキル全体に、2 つの設計ルールが適用されます。

1. **モデルが断ることのできる制御は、制御ではありません。** このスキルのすべての上限は、承認されたランタイムの経路で、署名の前に、Python で評価されます。
2. **ドキュメントは、コードが強制しない保証を主張してはなりません。** 以下のすべての主張は、それを実装する関数を名指ししており、両者が通知なしに乖離することはありません。

## ランタイムの設計

| 機能 | ここでは | セキュリティ上の性質 |
|---|---|---|
| `get_paid_content` | `x402_fetch(url)` — エージェントのツール | 同じ機能を、ポリシーのゲートの背後に置いた |
| `get_payment_session_status` | `payment_session_status()` — エージェントのツール | 趣旨は変わらない: 読み取り専用で、予算を作れない |
| ブラウザでの支払い | `prepare_browser_payment(url)` + `attach_browser_payment(handle, url)` | モデルは不透明な使い捨てのハンドルを受け取る。信頼できる接着コードがそれを使う |
| 支払いセッションを作成する | `agents_pay_admin.py new-session` — TTY を操作する人間 | セッションを発行できるランタイムには、累積の上限がない |
| インフラをプロビジョニングする | `agentcore` CLI のウィザード + `agents_pay_admin.py init-config` | プロバイダーのシークレットはツールのパラメーターに入らず、セットアップは実行時には存在しない |

ブラウザのフローは、はっきり述べる価値があります。証明が呼び出し元に届く必要がある唯一のケースだからです。モデルが受け取るのは、ハンドルであり、証明のバイト列ではありません。ハンドルは使い捨てで、90 秒で期限が切れ、1 つのオリジンとパスに結び付けられています。そのため、トランスクリプトから抜き出したハンドルを、別のリソースに使うことも、2 回使うこともできません。`attach_browser_payment` は本物のヘッダーを返すため、信頼できる接着コード用であり、モデルのツールセット用ではありません。

## セキュリティ制御と、その強制

| 制御 | 強制 |
|---|---|
| チャレンジの検証 | 厳密なスキーマ、設定されたスキームとネットワーク、正確なアセットのコントラクト、明示的な受取人のモード、`max_per_payment_usd` を下回る正準で正の金額、リソース/オリジンのチェックが、署名の前に強制される。競合する `amount` と `maxAmountRequired` のエイリアスは拒否される。署名者は、バージョンごとに正準な、1 つの金額フィールドを受け取る。通常のモードでは、`payTo` が `allowed_recipients` に含まれている必要がある。明示的な `allow_any_recipient: true` のモードは、受取人の選択を発行元に委ねる。 |
| シークレットの扱い | どのスクリプトも、シークレットの引数を受け付けない。プロバイダーの認証情報は、`agentcore` CLI のウィザードにのみ渡され、署名は AgentCore Payments の内部で行われる。`preflight` は、認証情報の形をした環境変数を拒否する。 |
| ネットワークの保護 | `assert_public_https_url()` と `assert_public_ip()` が、HTTPS を要求し、ループバック、RFC1918、リンクローカル、メタデータ、マルチキャスト、予約済み、未指定、CGNAT、v4 マップの形式を拒否する。`_PinnedResolverTransport` は、審査を通ったアドレスに接続する。リダイレクトは拒否され、本文のサイズは制限される。 |
| コンテンツの分離 | 支払い済みの本文は、デフォルトでは、モデルから見える出力から除外される。ランタイムは、ステータス、コンテンツタイプ、バイト数、SHA-256 のハッシュを返す。オペレーターは、設定ファイル(OS アカウントに紐づく、0600)で `return_body: true` を設定して、本文の返却を有効にできる。有効な場合、コンテンツは 10 KiB に制限され、`untrusted: true` と印が付けられる。認可がコンテンツを読むことはない。OpenClaw プラグイン(`get_paid_content`)も、同じように動作する。任意の `returnBody: true` のプラグイン設定フィールド(デフォルトは未設定/false で、現在と同じ動作)により、1 つのインストールが、同じ上限付きで `untrusted` と印が付いた本文の返却を有効にできる — オペレーターごとに設定し、モデルが制御することはできない。 |
| 冪等性 | `derive_client_token()` が、セッション、オリジン、パス、ネットワーク、アセット、受取人、金額をハッシュする。発行元のノンスは除外するため、リトライは同じ認可を再利用する。 |
| ロールの分離 | セッションの作成は `agents_pay_admin.py new-session` にのみ存在し、TTY がないと拒否され、`--yes` フラグもない。人間は **ManagementRole** を、エージェントはセッションの書き込みのない **ProcessPaymentRole** を使う。 |
| 証明の分離 | `x402_fetch` は、1 回のリクエストの間だけ、証明をローカルに保持する。ブラウザの経路は、1 つのオリジンとパスに結び付けられた、不透明な使い捨てのハンドルを返し、出力には編集済みのレシートだけが含まれる。 |
| ランタイムの面 | ランタイムの経路には、プロビジョニングやセッション作成のツールは存在しない。 |
| 再現可能なインストール | ランタイムの依存関係とバージョンの下限は文書化されている。テストは標準ライブラリのみ。完全な再現性を必要とするオペレーターは、ハッシュ付きのロックファイルからインストールすべき。 |
| ローカルの設定 | `_atomic_write_0600()` が、`0700` のディレクトリと `0600` のファイルを作成する。`load_config()` が、所有者、型、シンボリックリンク、書き込み可能な親を確認する。ランタイムのパス解決は OS アカウントを使い、`HOME`、`AGENTS_PAY_CONFIG`、`X402_POLICY_FILE` を無視する。ファイル内のリソースの値は、環境変数によるフォールバックよりも優先される。 |
| ドキュメントのチェック | この表は強制するコードを名指しする。`test_x402_policy.py` が動作を検証する。`preflight` がデプロイ済みの状態を確認する。 |

### 制御の限界

- **累積の上限。** セッションごとの予算と、人間だけがセッションを作成できることによって、セッションごとの支出に上限がかかり、セッションの間に人間が介在することが強制されます。しかし、複数のセッションにまたがる*サービス側の*累積の上限ではありません。それには、スキルの手の届かない、AgentCore Payments のサポートが必要です。10 個のセッションを承認したオペレーターは、10 個の予算を承認したことになります。
- **依存関係の固定。** スキルのフォルダは、ホスト環境が尊重する Python のロックファイルを同梱できません。再現性を求めるオペレーターは、ハッシュ付きの `requirements.txt` からインストールするか、`pip install --require-hashes` を使うべきです。スキルは下限を示しますが、解決を強制することはできません。
- **DNS リバインディング。** IP の固定は、審査を通ったアドレスに接続することで、一般的な TOCTOU の隙を塞ぎます。支払い可能なエージェントには、ネットワークレベルのエグレスの許可リストのほうが強力な制御であり、置き換えられるのではなく、推奨されます。

  残しておく価値のある実装上の注意: 固定は、`socket.getaddrinfo` を一時的に置き換えることで実装しては**なりません**。そのグローバルは共有されているため、2 つの同時の取得が、互いの状態を復元したり観測したりして、リクエストが*固定されていない*状態で解決されてしまい、通知なしに隙が再び開く可能性があります。そのため、固定は、トランスポートごとに存在する、コネクションプールのネットワークバックエンドに置かれています。`test_pin_is_not_implemented_by_patching_a_global` が、この回帰を防いでいます。
- **同一アイデンティティでのコード実行。** ランタイムの OS アイデンティティと AWS 認証情報を持つプロセスは、オーナーが書き込めるファイルを変更したり、支払い SDK を直接呼び出したりできます。モデルを登録されたツールに限定するか、署名者とポリシーを、別のプロセス、コンテナ、OS アカウント、IAM ロールの背後に置いてください。

## 単一の設定ファイルと、固定されたランタイムのパス

リソースの識別子と支払いポリシーは、オペレーターが所有する単一のファイル、`~/.agents-pay/config.json`(`0600`、`0700` のディレクトリ内、アトミックに書き込み)にあります。

```json
{
  "resources": { "payment_session_id": "ps-...", "payment_manager_arn": "arn:...", ... },
  "policy":    { "max_per_payment_usd": "0.05", "allowed_networks": ["eip155:84532"], ... }
}
```

最初は別々で、オペレーターは、ステップ間で識別子を手でコピーする必要がありました。統合してそれをなくしましたが、名前を挙げる価値のある制御も得られました。

**セッション ID は、支出の認証情報です** — 消費される予算を指し示すからです。`runtime_config_path()` は、`.agents-pay/config.json` を OS アカウントから解決し、`HOME`、`AGENTS_PAY_CONFIG`、`X402_POLICY_FILE` を無視します。`resolve_resource()` は、通常とは意図的に逆の優先順位で、**先に設定ファイルを、次に環境変数を**読み取ります。

固定されたポリシーファイルに記載がない場合は、コンテナや Lambda がリソースの識別子を注入できます。環境変数が、代わりのポリシーファイルを選択することはできません。ファイルのモードが守るのは、他のプリンシパルからです。オーナーとしてすでに動作している制限のないコードに対しては、より強力なプロセス、コンテナ、OS アカウント、IAM の境界が必要です。
*テスト: `test_runtime_ignores_environment_selected_policy_file`、`test_runtime_config_path_ignores_home_environment`、`test_config_file_beats_environment`。*

## 受取人の検証

通常のモードでは、発行元が指定した受取人(`payTo`)が、オペレーターが承認した `allowed_recipients` のエントリと一致する必要があります。受取人のポリシーがない、または空の場合は、すべての支払いが拒否されます。オペレーターは代わりに、`allow_any_recipient: true` を設定して、受取人の選択を明示的に発行元に委ねることもできます。両方のモードは排他的で、ブール値以外の値は、安全側に倒れて拒否されます。

オープン受取人のモードは、スキーム、ネットワーク、正確なアセット、オリジン/リソース、1 回あたりの上限、セッションの累積の制御を緩和しません。ただし、受取人についての決定的な境界は取り除かれるため、オペレーターによる、意図的でリスクの高い選択です。

`RecipientValidationTests` は、未知の受取人の拒否、許可リストがない場合の拒否、大文字小文字を区別しない一致、オープン受取人の受け入れ、モードの競合、不正な値、その他のポリシーチェックの維持を網羅しています。

## オリジンは任意

HTTPS のみ、内部アドレスの拒否、リダイレクトの手動処理、DNS リバインディングへの対策、タイムアウト、厳格なバイト数の上限は、無条件に強制されます。承認されたドメインのエグレスポリシーは、支払い可能なエージェントにとって追加の保護になりますが、必須ではありません。

したがって、`allowed_origins` は**任意**です。未設定なら、公開されている任意の HTTPS サイトを意味し、既知の加盟店の集合があるデプロイでは、それに固定することもできます。*テスト: `OptionalOriginTests`。*

## 2 つの上限は、重複ではない

もっともな疑問があります。セッションにはすでに予算があるのに、なぜポリシーにも `max_per_payment_usd` があるのか。

それらは、異なるものを制限するからです。

| 上限 | 範囲 | 設定する場所 |
|---|---|---|
| セッションの予算 | **累積** — 人間が再承認する必要があるまでの総支出 | `new-session`、入力による承認 |
| `max_per_payment_usd` | **1 回のトランザクションごと** | ポリシーのセクション |

セッションの予算だけだと、悪意のある加盟店が、残りの全額を要求するチャレンジを 1 つ返し、1 回の支払いで使い切られてしまいます。1 回の支払いごとに、信頼できる正の最大値があることで、1 回あたりの上限は、冗長ではなく、必要なものになります。1 回あたりの上限がない場合は、上限のない支払いではなく、拒否になります。
*テスト: `test_missing_per_payment_cap_refuses_rather_than_paying_unbounded`。*

## ロールの分離が、本当の境界

このスキルの制御が意味を持つのは、[公式のガイド](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/payments-iam-roles.html)が説明する IAM の分離が、アカウントで維持されている場合に限られます。

| ロール | 保持するもの | 保持してはならないもの |
|---|---|---|
| **ManagementRole** — 人間 | instrument とセッションの Create/Get/Delete | `ProcessPayment`(明示的な `Deny`) |
| **ProcessPaymentRole** — エージェント | `ProcessPayment`、instrument/残高/セッションの Get | セッションの**書き込み**のすべて |

**エージェントは、ManagementRole を持ってはならず、`agents_pay_admin.py` を実行できてもなりません。** 両方を持つ場合、予算を使い切るたびに新しい予算を発行でき、セッションごとの上限は何も制限しません。

`new-session` の TTY の要件は、多層防御であり、境界ではありません。オペレーター自身のユーザーとして対話型のターミナルで動作しているエージェントは、それでも操作できてしまう可能性があります — それを実際に止めるのは IAM であり、ランタイムのロールが `CreatePaymentSession` を除外しなければならない理由です。

## 1 つの文書を検証して、別の文書に署名する

ゲートがチャレンジを完璧に検証していても、*署名者*に別のものが渡されるなら、役に立ちません。

x402 のチャレンジには、複数の `accepts` のエントリがあることがあり、条件が `payment-required` ヘッダーにも本文にも現れることがあります。信頼できるコードが 1 つのエントリを検証しながら、発行元の生のレスポンスを `generate_payment_header` に転送すると、SDK は、ポリシーが見ていない条件を決済してしまうかもしれません。

- **順序。** `accepts[0]` = 攻撃者への $50、`accepts[1]` = 加盟店への $0.10。ゲートはエントリ 1 を承認して $0.10 と報告しますが、両方を渡された署名者は、エントリ 0 を決済します。
- **ヘッダーと本文の食い違い。** 準拠したヘッダーと、悪意のある本文。ゲートはヘッダーを読んで承認し、署名者は本文を読んで、別のチェーンでのより大きな金額を承認します。その後、レシートはオペレーターに*嘘をつきます*。

どちらも、通知がありません。返されるレシートは、署名されたものではなく、承認されたエントリを反映します。ゲートの戻り値だけを検証するテストは、悪用が機能していても合格してしまう可能性があります。

修正は構造的なものです: `x402_policy` は、競合する金額のエイリアスを拒否し、バージョンごとに正準な、審査済みのエントリを組み立てます。`x402_fetch` は、その単一のエントリを、新しい最小限のチャレンジ(`{"x402Version": ..., "accepts": [vetted]}`)として再シリアライズし、合成した `content-type` ヘッダーと共に、それだけを渡します。`SignerInputTests` は、ゲートの戻り値だけでなく、署名者に渡されるオブジェクトを検証します。

**`scripts/` を変更する人へのルール:** 署名者が受け取るデータは、信頼できるコードが構築したものでなければならず、発行元が提供したものであってはなりません。

## 検証

```bash
python3 scripts/test_x402_policy.py                 # すべて合格すること
python3 scripts/agents_pay_admin.py show-config      # 0600 と内容を確認する
python3 scripts/agents_pay_admin.py preflight        # 組み込みとシークレットの露出
```

再現可能な証拠は次のとおりです: テストスイートの合格、`show-config` のトランスクリプト、受取人が意図的に許可リストにない、実際のエンドポイントに対して取得した拒否。

## オペレーターが引き受ける残存リスク

- **ポリシーは、許可リストの厳密さ以上には厳密になりません。** 緩いポリシー(多数の受取人、高い上限)は、コードによって許可されており、オペレーターのリスクです。
- **まずテストネットで。** デフォルトは Base Sepolia を対象とします。メインネットに移行すると、実際のお金が動きます。`--network` を切り替える前に、上限を再確認してください。
- **ウォレットの入金額は、最後の手段としての上限です。** エージェントが支出する可能性のある金額だけを入金してください。他のすべての制御が失敗した場合の、最後の砦です。
- **ホストやランタイムのロールの侵害は、対象外です。** ランタイムのアイデンティティとして任意のコードを実行できる、所有者としてポリシーを変更できる、プロセスのメモリを読める、`ProcessPayment` を直接呼び出せる攻撃者は、このローカルのゲートを回避できます。
